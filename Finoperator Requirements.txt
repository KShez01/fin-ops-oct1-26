# Python Financial Processing Engine
## Master Product, Financial, Architecture and Development Instructions

---

# 1. YOUR ROLE

Act as the Principal Financial Systems Architect and Lead Python Backend Engineer responsible for designing and implementing a production-grade financial batch-processing and ledger engine.

This is not a generic CRUD application and not merely a batch-file parser.

The completed system must be capable of receiving financial instructions, resolving the correct customer/program relationship, applying deterministic financial policy, protecting funds from double use, creating balanced accounting evidence, planning external money movement, reconciling results, notifying external partners, and preserving enough durable evidence to explain every outcome later.

Operate conservatively around money.

When a business rule materially affects:

- who owns value;
- whether value is available;
- whether value may be consumed;
- how much money moves;
- how a refund is funded;
- how accounting is posted;
- how a reversal behaves;

do not invent the missing rule.

Record an `OPEN_QUESTION` and continue only with work that does not depend on that unresolved financial decision.

---

# 2. PRODUCT OBJECTIVE

Build a Python financial engine that can process customer-level Clearing and Settlement files end to end.

The conceptual lifecycle is:

```text
Receive
→ Preserve Evidence
→ Parse
→ Normalize
→ Validate
→ Resolve Customer / Program
→ Identify Instruction
→ Resolve Dependencies
→ Decide Financial Treatment
→ Evaluate Availability
→ Reserve
→ Create Financial Transaction
→ Post Accounting
→ Update Financial Positions
→ Create Durable Follow-Up Work
→ Plan Money Movement
→ Reconcile
→ Notify
→ Audit
```

The engine must always be able to answer:

```text
What instruction arrived?

Where did it come from?

Which customer/program did it belong to?

Was the instruction valid?

Was it already processed?

What business/root transaction did it relate to?

What financial value did it represent?

Which financial positions supported it?

Was value reserved?

Which financial positions changed?

Which journal entries prove those changes?

What external money movement was required?

Was a payment file generated?

Did the bank actually settle it?

Was the external partner notified?

Can the full result be reconstructed later?
```

If durable system evidence cannot answer these questions, the implementation is incomplete.

```text
5. retry/idempotency identity
```

Do not establish one universal formula such as:

```text

```

Mandatory identity fixtures include:

```text

→ duplicate-safe

→ allowed when financially eligible

same business authorization + later CPC
→ allowed when financially eligible

same business authorization + refund
→ allowed when financially eligible

→ rejected
```

Authorization/root references are primarily relationship identifiers.

They are not automatically idempotency identifiers.

# 31. RESERVATION MODEL

Create:

```text
Reservation

id

transaction_id

customer_program_id
financial_position

amount
currency

status

created_at
captured_at
released_at
cancelled_at
```

Statuses:

```text
CONTINGENT
ACTIVE
CAPTURED
RELEASED
CANCELLED
```

Meaning:

## CONTINGENT

The transaction is waiting for expected financial support or another prerequisite.

It does not mean the money is presently secured.

It must not reduce presently available posted funds unless the specific financial policy explicitly says otherwise.

## ACTIVE

Existing value has been allocated to the transaction.

It reduces availability.

## CAPTURED

The committed accounting posting consumed the reserved position.

## RELEASED

Previously allocated value has returned to availability.

## CANCELLED

The reservation became permanently unnecessary before capture.

Processing status and reservation status are separate concepts.

A `BLOCKED` transaction may have:

```text
no reservation
CONTINGENT reservation
ACTIVE reservation
```

depending on policy.

Reservation capture and the posting that consumes the value must be atomic.

# 32. CPP

CPP settles collected partner fee claim.

Requested gross:

```text
PartnerFee
```

Eligibility:

```text
available PARTNER_FEE_CLAIM
>= gross requested
```

A transaction may become blocked/contingent if the referenced incoming financial support is pending and policy permits such treatment.

Processor fee is calculated using:

```text
SettlementFeePolicy
```

Then:

```text
partner_net_payout_amount
=
gross_accepted_amount
-
settlement_processor_fee_amount
```

Economic result:

```text
PARTNER_FEE_CLAIM decreases by gross claim consumed

PARTNER_EXTERNAL increases by partner net

PROCESSOR_REVENUE increases by processor fee
```

Invariant:

```text
gross claim consumed
=
partner net payout
+
processor fee
```

# 34. CPC

CPC represents program-completion settlement.

Gross request:

```text
PartnerFee
```

Eligibility uses supported value from:

```text
PARTNER_FEE_CLAIM
+
CUSTOMER_PRINCIPAL
```

The transaction must record the exact allocation.

Default deterministic economic allocation requirement:

```text
consume eligible partner fee claim

then consume required remaining amount
from customer principal
```

Do not silently choose another order.

If business acceptance fixtures define another order, the fixture wins and this rule must be revised explicitly.

Allocation components must equal the gross accepted CPC amount.

Then calculate:

```text
settlement processor fee
partner net payout
```

A program completion obligation cannot be consumed twice.

# 39. CPRRWX

CPRRWX is system-derived.

It can represent an extended refund route that may unwind value associated with:

```text
PARTNER_EXTERNAL
PROCESSOR_REVENUE
PARTNER_FEE_CLAIM
```

before establishing a customer refund.

Do not accept it externally unless explicitly enabled.

---

# 40. CPCN

CPCN represents cancellation/unwind of completion-related financial history.

It must relate to an actual prior economic completion.

It may need to unwind:

```text
PARTNER_EXTERNAL
PARTNER_FEE_CLAIM
PROCESSOR_REVENUE
```

and restore/refund eligible customer value.

Never create greater refund or restored value than the remaining reversible economic effect.

---

# 41. PFP

PFP is system-generated.

It represents the processor-fee component associated with a parent settlement.

Store:

```text
source = SYSTEM
parent_transaction_id
```

Its amount must equal the processor fee attributed to the parent transaction.

It must never independently consume customer principal.

---

# 42. VPF

VPF is system-generated control activity for a processor-fee expectation that must be held, voided or unwound because its parent settlement/refund lifecycle changed.

It is not customer money.

It must always identify its financial parent.


# 49. FINANCIAL POSITIONS

Journal entries are authoritative.

Maintain materialized FinancialPosition rows for fast execution.

Expose:

```text
posted_balance
reserved_balance
available_balance
```

where:

```text
available
=
posted
-
active reservations
```

according to the account's economic interpretation.

Materialized positions must always be rebuildable from:

```text
journal
+
active reservation state
```

Never directly edit a position to fix accounting history.

---

# 50. FINANCIAL COMMIT BOUNDARY

For one financial transaction, the following operations must form one PostgreSQL transaction where applicable:

```text
lock affected financial positions

re-read posted/reserved values

validate availability

make financial decision

create/update FinancialTransaction

create/update financial reservation

create Posting

create all PostingLines

update materialized FinancialPosition

capture/release relevant reservations

persist DecisionRecords

create required durable follow-up WorkflowJobs

COMMIT
```

Either all durable financial-state changes commit or none commit.

Do not permit:

```text
reservation commits
posting fails
```

or:

```text
posting commits
required next-work disappears
```

External HTTP calls, SFTP movement and external bank operations must not occur inside this financial transaction.

---

# 51. CONCURRENCY

Financial consumers must protect positions through PostgreSQL locking.

Typical execution:

```text
BEGIN

lock affected position rows

re-read balances

re-read active reservations

validate eligibility

create reservation/posting/state changes

COMMIT
```

Two workers must never consume the same economic value.

Required example:

```text
available = 100

request A = 80
request B = 80

successful total <= 100
```

Run real PostgreSQL concurrency tests.

Do not prove this only through mocked unit tests.

---

# 52. COMPETING INSTRUCTION PRIORITY

Database locking prevents overspending but does not itself define business priority.

Competing accepted instructions against the same financial support must have a durable, explainable priority.

The exact mechanism is an implementation choice.

Examples include:

```text
admitted_at
batch sequence
source row sequence
dedicated monotonic sequence
```

The design must ensure that worker scheduling or random lock acquisition does not become undocumented financial business logic.

Document the selected ordering strategy before implementation.

# 54. FAILURE RECOVERY

Design every workflow as:

```text

→ create durable next work
→ perform external/asynchronous work
```

```text

→ no partial financial result

after commit
→ durable workflow job remains available
```

Every retry must be idempotent.

# 94. AGENT WORKING RULES

Follow these rules throughout development.

1. Treat this prompt as the product and architecture specification.

2. Treat supplied business acceptance fixtures as normative financial examples.

3. Do not assume another application's internal architecture.

4. Do not reproduce another application's defects.

5. Do not invent undefined rules that change money.

7. Continue unrelated implementation work where possible.

8. Never use float for financial values.

9. Never directly overwrite authoritative financial balances.

10. Never edit/delete posted journal records.

11. Never commit a partial posting.

12. Never calculate availability without considering active reservations.

13. Never let retry duplicate a financial effect.

# 98. ENGINEERING STANDARD

The implementation should favor:

```text
explicitness over cleverness

financial semantics over generic abstraction

small policy components over giant processors

database guarantees over optimistic assumptions

immutable evidence over mutable history

deterministic recovery over manual repair

semantic monetary names over ambiguous amount fields

traceability over convenience

controlled scope over speculative architecture
```

The objective is not to create the largest possible financial platform.

The objective is to create the smallest system that correctly, safely and explainably executes the defined financial behavior and can be expanded one controlled capability at a time.
